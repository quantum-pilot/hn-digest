# If you thought code writing speed was your problem you have bigger problems

- Score: 294 | [HN](https://news.ycombinator.com/item?id=47415919) | Link: https://andrewmurphy.io/blog/if-you-thought-the-speed-of-writing-code-was-your-problem-you-have-bigger-problems

### TL;DR

Applying Goldratt’s Theory of Constraints, the author argues that faster code generation cannot improve delivery when reviews, CI, deployment, product discovery, feedback, or decision calendars are the bottleneck. It instead raises work-in-progress, context switching, rubber-stamping, incident risk, and cycle time while dashboards celebrate code output. Leaders should map idea-to-user value streams, measure waiting rather than lines or PRs, cap concurrent work, and remove the actual queue. HN agreed that agents excel at prototypes and tedious transformations, but debated whether parallel agent work aids learning or mainly creates cognitive overload.

### Comment pulse

- Cheap prototypes can clarify requirements → contact with users or a failing demo teaches quickly — counterpoint: customer feedback loops may be scarce and expensive.
- Agent sweet spots emerged → analogous changes, contextual replacements, edge cases, and exploratory refactors benefit more than ambiguous product decisions.
- Parallel work divides developers → agents fill idle time, but constant review and context switching can reduce focus, satisfaction, and quality.

### LLM perspective

- **View:** Local coding acceleration matters only when the constrained stage receives less work or gains comparable capacity.
- **Impact:** Engineering leaders must replace output dashboards with cycle time, queue age, WIP, adoption, and incident measures.
