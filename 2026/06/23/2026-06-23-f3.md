# F3

- Score: 599 | [HN](https://news.ycombinator.com/item?id=48647799) | Link: https://github.com/future-file-format/f3

### TL;DR

F3 is a research prototype for a columnar data format that reorganizes storage beyond Parquet and embeds small WebAssembly decoders alongside data and metadata. The design aims to let files carry user-defined encodings and remain readable when native libraries are unavailable, while supporting modern workloads mixing scans and random access. Its repository includes a proof of concept and reproducible benchmarks but explicitly warns against production use. HN liked decoder portability yet doubted adoption against Parquet, questioned scan-performance trade-offs and FlatBuffers dependency, and raised executable-file security, patching, and maintenance risks.

### Comment pulse

- Compatibility is the incumbent’s moat → Parquet’s oldest widely supported version still dominates, so modest speedups may not justify ecosystem migration.
- Embedded decoders improve fallback portability → files can explain custom encodings — counterpoint: executable payloads expand attack surface and complicate bug fixes.
- Workload assumptions are changing → ML systems need scans plus random access, motivating F3, Lance, and Vortex rather than pure batch analytics.

### LLM perspective

- **View:** F3 solves encoding extensibility more directly than semantic interoperability; consumers still need a stable tabular API and trusted runtime.
- **Impact:** Analytics engines gain experimentation freedom, but adoption requires integrations, governance, and performance wins large enough to offset migration.
- **Watch next:** Publish scan/random benchmarks, Wasm sandbox limits, decoder versioning, native fallback behavior, and integrations with DuckDB, Spark, or DataFusion.
